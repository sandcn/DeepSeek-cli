# 跨对话记忆系统使用指南

两级记忆文件（索引+详情），按规则自动维护。`memory.md` 须主动读取。

> **强制读项目目录（行为优先级 #0）**：任何操作前，先读记忆（按本指南），再通过 `find` 获取项目完整目录结构。`find` 的 `depth` 参数**不传**（即无限制递归），确保全量探底，建立对项目全貌的认知。例如：`find(pattern="*", path=".", type="dir")`。首次使用/新项目无记忆文件时可跳过记忆读取，但目录探底仍需执行。

## 文件结构

    .chat/memory/
      memory.md      ← 索引（标题+摘要≤150字+链接）
      mem_XXXX.md    ← 详情（精简）

**不存在则创建（强制）**：首次使用时，若 `.chat/memory/memory.md` 不存在，须创建 `.chat/memory/` 目录并写入初始 `memory.md`（空索引，仅含标题行和注释说明「首次创建于 YYYY-MM-DD」），禁止直接跳过。初始 `memory.md` 内容模板：

    # 记忆索引
    <!-- 首次创建于 YYYY-MM-DD，后续按规则维护 -->

## 读取
- **查索引** → `read_file .chat/memory/memory.md`
- **读详情** → 从索引链接取路径，`read_file` 全文
- **搜记忆** → `search query="关键词" path=".chat/memory/" include="*.md" max_results=500`

## 验证（记忆是参考非权威）
- **时效**：7天内高置信度，≥90天未验证默认过时
- **交叉验证**：含代码路径/函数名时 `search` 确认
- **置信度**：100%（已验证） / ≥80%（高） / <80%（推断）
- **过时处理（强制）**：把最新的更新到记忆文件；若无新信息可写入（当前对话未涉及该模块），标注「过时-无可用更新」后跳过

## 使用
1. 用前验证并标注置信度
2. 过时则更新
3. 引用说明来源，关键信息向用户确认
4. 禁止：不验证直接引用 / 只看摘要不读详情 / 虚构 / 过度引用

## 维护

### map SubAgent 调度规范

> **核心规则（强制）**：派发 map SubAgent 分析多个目标时，必须按目录文件分组、分批、强制并行执行。

#### 1. 按目录文件分组（强制）
当需同时派发多个 map SubAgent 分析不同文件/模块时，**必须按目标所在的目录进行分组**——同一目录下的文件归为一组，同轮并发派发。

**分组依据**：
- 文件路径的目录层级（如 `src/module_a/` 下的所有文件为一组）
- 同一模块的多个关联文件（如 `src/module_a/__init__.py` + `src/module_a/core.py`）
- 同一调用链上下游（如调用方与被调用方同属一个模块组）

```
# 正确：按目录分组并发
dispatch_agent(type="map", description="分析: src/module_a", prompt="分析 src/module_a/ ...")
dispatch_agent(type="map", description="分析: src/module_b", prompt="分析 src/module_b/ ...")

# 错误：未按目录组织，杂乱派发
dispatch_agent(type="map", description="分析: 文件_x", ...)
dispatch_agent(type="map", description="分析: 文件_y", ...)
```

> **问责闭环**：分组不按目录归并（同目录文件拆分到不同轮次派发）视为调度缺陷，部署审查时将标记。

#### 2. 分批执行（强制）
同轮并发派发的 map SubAgent 数量**上限 8 个**。超过 8 个时必须按目录分组分批。

**分批策略**：
- **优先合并同目录**：同目录下的多个文件尽量合并到一个 map SubAgent 的 prompt 中分析，而非每个文件单独派发一个 map
- **按目录分批**：超过 8 个目录时，按目录的自然顺序分批（第 1-8 组一批，第 9-16 组一批，以此类推）
- **跨轮次分批**：第一批完成后立即派发第二批，避免不必要的等待间隔

```
# 示例：12 个目录分两批
# 第 1 轮（并发 8 个）
dispatch_agent(type="map", description="分析: dir_01..08", ...) ×8

# 待第 1 轮全部返回后
# 第 2 轮（并发 4 个）
dispatch_agent(type="map", description="分析: dir_09..12", ...) ×4
```

> **资源保护**：≥8 个时不分批可能引发文件系统吞吐瓶颈或内存压力，按此规则强制分批。

#### 3. 强制并行（强制）
同轮派发的 map SubAgent（不混用其他工具）必须**同轮多次 `dispatch_agent` 并发派发**，禁止逐个串行派发。

**判定标准**（满足任一即触发）：
- 同时需要分析多个独立目录/模块
- 多个分析目标之间无先后依赖关系
- 多个 map 分析目标已同时确定

**与分批的协同**：分批后，每批内的多个 map SubAgent 仍然必须同轮并发派发。禁止将一批内的多个 map 拆成多轮串行。

```
# 正确：批内并发
# 第 1 轮（批：8 个 map 并发）
dispatch_agent(type="map", ...) # 文件 A
dispatch_agent(type="map", ...) # 文件 B  ← 同轮并发
dispatch_agent(type="map", ...) # 文件 C
...

# 错误：批内串行
dispatch_agent(type="map", ...) # 文件 A → 等待 → 再发文件 B → 等待 → 再发文件 C
```
> **并发上限**：单轮并发控制在 8 个以内，避免文件系统吞吐瓶颈。

### 核心原则（强制）
- **变化即更新**：状态变更时同步更新条目（`update_file` 替换详情 + 刷新时间戳）
- **新增优先合并**：搜 `memory.md` + 详情文件，能合不合则另建。**新条目要优先合并到旧条目里面**，而非另建新条目
- **代码修改强制记录**：有逻辑影响的代码变更（新增功能/修改行为/删除逻辑/重构接口/修复 Bug）完成后**必须**同步创建或更新记忆条目（内容+动机+影响范围），禁止"只改不记"。纯排版/typo/注释调整等零逻辑变更可豁免

### 触发条件（命中即记）
以下**必须**创建或更新记忆条目：
1. **代码修改（强制）** — 有逻辑影响的代码文件变动（排版/typo/纯注释调整豁免）。按模块粒度记录：同一模块的多次修改合并为一条"<模块名> 修改记录"条目，每次追加时间戳和变更摘要
2. 用户明确偏好 / 技术决策 / 项目约定 / 已修复 Bug / 用户要求记录 / 重复需求 / 架构变更

### 操作流程
- **新增**：搜 `memory.md` → 有则合并，无则创建 `mem_XXXX.md` → 追加索引
- **更新**：`update_file` 替换详情 + 刷新时间戳
- **删除**：清理索引 + `rm` 详情文件
- **合并**：同主题多条合并去重，保留最新时间戳。来源索引行追加 `<!-- merged to mem_XXXX.md at YYYY-MM-DD -->`

### 数量控制
上限1000条（不含已归档条目）：≥800 合并 → ≥900 清理过期 → ≥950 全量整理。代码修改条目按模块组织（同模块多次修改合并为单条目追加），控制增长速度。

### 保护等级
- [锁定] P0 永不淘汰：偏好/决策/约定 → 不可归档/删除
- [锁定] P1 建议复审（180天）：Bug/选型 → 不可删除，可归档
- [开放] P2 正常淘汰：一次性问答/临时状态 → 可归档可删除

### 归档
- 索引前加 `[ARCHIVED at YYYY-MM-DD]`，摘要末尾追加原因
- 详情文件**保留在原位置**，索引链不变
- Agent 跳过 `[ARCHIVED]`，需要时仍可通过 search 检索
- 已归档条目不计入数量控制统计。归档超过 365 天的条目允许物理删除详情文件（索引行加 `[ARCHIVED+DELETED at YYYY-MM-DD]` 标记）
